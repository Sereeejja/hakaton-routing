# Уточнения требований из чата задачи

Документ фиксирует только ответы организаторов, влияющие на продукт. Сообщения
участников не трактуются как требования.

| Уточнение | Реализация |
|---|---|
| Каждый регион и офис — независимый сценарий | Зоны загружаются и оптимизируются отдельно |
| Старт из офиса, возврат после последней заявки не требуется | Открытые маршруты с отдельным стартом |
| Любая строка, включая информацию/мониторинг, считается выездом | Политика `field_service` включена по умолчанию; альтернативу можно настроить явно |
| Приоритет: авария → подключение → ремонт/дозаказ | Лексикографические штрафы в OR-Tools/HGS и тот же порядок в эвристике |
| Авария определяется по `request_type_hd` | `Тип заявки HD = Авария` получает срочный приоритет |
| Авария может вытеснять обычные заявки | Срочность доминирует над полнотой обычных заявок при перепланировании |
| Динамическая авария должна быть обработана за 1–2 часа | API поддерживает событие `new_urgent_request`; окно реакции задаётся временем события и SLA |
| График задаётся на уровне бригады: `2/2` или `5/2` | Поле `work_schedule` хранится в PostgreSQL/API; типовые смены 10:00–22:00 и 09:00–18:00 |
| Время дороги заменяет нормативные 20 минут | Матрица маршрутизации определяет travel time, сервисный норматив дорогу не дублирует |
| Транспорт: авто, пешком, велосипед, общественный | Все четыре режима есть в API, мастер-данных и модели времени |
| Контрольное распределение — ориентир, не обучающий ответ | Оно исключено из входа оптимизатора; сравнение ведётся с прозрачным baseline |
| Начало работы должно попасть в окно; завершение может выйти за окно | Валидатор ограничивает `service_start`, а конец — границей смены |
| Дополнительные дни содержат ошибки в названиях/датах | Дата читается из строки заявки; результаты аудита вынесены отдельно |

Внутренние параметры оптимизатора (название алгоритма, seed и лимит времени)
остаются серверными настройками и не показываются диспетчеру.
